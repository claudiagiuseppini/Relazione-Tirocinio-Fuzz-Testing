# Vulnerability Discovery with Fuzz Testing

This repository contains the work developed for my Bachelor's thesis in **Computer Engineering and Automation at Sapienza University of Rome**.

The project investigates the use of **coverage-guided fuzzing** and **dynamic memory analysis** to discover software vulnerabilities in open-source projects, with particular attention to **Use-of-Uninitialized Memory (UUM)** errors.

## Project Goals

The main objectives of the project were to:

* detect software bugs through automated fuzz testing;
* investigate Use-of-Uninitialized Memory vulnerabilities;
* evaluate the effectiveness of **QMSan** during fuzzing;
* reproduce and analyse crashes generated by the fuzzer;
* distinguish duplicate crashes from unique bugs;
* verify whether discovered issues had already been reported;
* responsibly disclose previously unknown vulnerabilities to project maintainers.

## Technologies and Tools

The project makes use of:

* **AFL++** — coverage-guided fuzzing;
* **QMSan** — detection of uninitialized-memory errors;
* **Valgrind** — memory-error analysis and crash investigation;
* **GDB** — debugging and stack-trace analysis;
* **Docker** — isolated and reproducible testing environments;
* **Python** — automation and crash deduplication;
* **OSS-Fuzz** — seed corpora and comparison with existing reports;
* **Google Fuzzer Test Suite** — validation of the experimental setup.

The experiments were performed using Ubuntu 22.04 virtual machines. Docker environments were separated into components for the AFL++ toolchain, QMSan, and the software under test.

## Methodology

The project followed the workflow:

```text
Environment Setup
        ↓
Fuzzing Campaign
        ↓
Crash Collection
        ↓
Crash Reproduction
        ↓
Memory Analysis
        ↓
Crash Deduplication
        ↓
Manual Triage
        ↓
Known-Issue Verification
        ↓
Responsible Disclosure
```

### Environment Setup

Dedicated Docker images were created to make the experiments reproducible and comparable across different targets.

The setup was initially validated using programs from the **Google Fuzzer Test Suite**.

### Fuzzing

The main fuzzing campaigns used **AFL++ integrated with QMSan**.

AFL++ generates and mutates test inputs while using code-coverage feedback to identify inputs that explore new execution paths.

Two seed strategies were tested:

* simple synthetic or "dummy" seeds;
* corpora obtained from OSS-Fuzz.

The OSS-Fuzz corpora were particularly important for complex applications because they allowed the fuzzer to reach deeper program states.

### Crash Analysis

Generated crashes were reproduced and analysed with QMSan and Valgrind.

Since multiple inputs can trigger the same underlying bug, the number of crashes cannot be interpreted directly as the number of vulnerabilities.

Crash traces were therefore grouped and deduplicated before manual analysis. A Python script was used for an initial clustering step based on the first stack frames, followed by manual triage of the remaining crash groups.

The main open-source targets were:

| Project  | Fuzzing Target          |
| -------- | ----------------------- |
| GPAC     | `fuzz_probe_analyze`    |
| LibreDWG | `llvmfuzz`              |

The main fuzzing campaigns typically ran for approximately **36 hours**.

## Results

The experiments generated more than **600 crashes** across the analysed projects.

| Project  | Raw Crashes |
| -------- | ----------: |
| GPAC     |          33 |
| LibreDWG |         437 |
| LibUCL   |         191 |
| OpenSC   |          16 |

A significant portion of these crashes were duplicates, non-reproducible, or related to bugs that had already been fixed or reported.

This highlights an important distinction:

```text
Crash ≠ Bug ≠ Vulnerability
```

A large number of crashes does not necessarily correspond to a large number of unique software vulnerabilities.

## OpenSC Case Study

OpenSC produced some of the most relevant findings.

After removing duplicate, non-reproducible, and already known crashes, three unique issues remained.

The observed errors included:

* use of uninitialized values;
* conditional operations depending on uninitialized values;
* invalid memory reads.

These results demonstrated the usefulness of combining fuzzing with memory sanitizers for detecting bugs that may not be visible through conventional testing alone.

## Why QMSan?

The project focused particularly on **Use-of-Uninitialized Memory** errors.

QMSan builds on concepts used by MemorySanitizer while operating through **QEMU User Emulation**. Unlike approaches that require all dependencies to be recompiled with instrumentation, QMSan can operate at the binary level.

This makes it useful when analysing:

* third-party software;
* libraries that cannot easily be rebuilt;
* complex dependency chains;
* binary software without complete source instrumentation.

Its multi-layer approach attempts to balance detection accuracy with runtime performance.

## Crash Deduplication and Triage

A major part of the project involved reducing hundreds of raw crashes to a smaller set of meaningful findings.

The process included:

1. reproducing crashes;
2. collecting stack traces;
3. grouping crashes according to stack information;
4. removing duplicate cases;
5. discarding non-reproducible crashes;
6. analysing remaining cases manually;
7. checking project repositories for previously reported issues.

This step was essential because many different fuzzing inputs can trigger the same underlying software defect.

One of the main lessons from the project is that **finding crashes is only the first step of vulnerability research**.

A crash must still be analysed to determine:

1. whether it is reproducible;
2. whether it is a duplicate;
3. what caused it;
4. whether it represents a real software bug;
5. whether the bug has security implications;
6. whether the issue is already known.

## Conclusion

The project demonstrated that combining **coverage-guided fuzzing with sanitizers** can effectively uncover memory-related bugs that may be difficult to identify through conventional testing.

The experiments also showed that automated vulnerability discovery requires substantial post-processing: hundreds of raw crashes may ultimately correspond to only a small number of meaningful and unique findings.

QMSan proved effective in detecting Use-of-Uninitialized Memory errors during the experiments, while fuzzing provided the large number of executions necessary to explore unexpected program behaviour.
